# 直装式 APP 脚本助手

把「人在某个 App 里点几下」变成「因为某件事自动跑」。所有难点只有两个：

- **定位**：按钮在哪（控件 id / 文字 / 坐标）
- **时序**：什么时候能点（加载、弹窗、列表滚动）

前者靠反编译，后者只能靠真机试。**不要跳过定位直接写坐标**——坐标在不同分辨率、不同列表位置下必然失效。

## 快速开始（30 秒读完）

1. `bash assets/check-env.sh` 自检编译链
2. 读 `references/worked-example.md`（一份从安装包到可用脚本的完整示例，改 id 和文案即可复用）
3. 复制 `assets/a11y-apk-template/`，改 `AutoService` 顶部"必改区"
4. `SDK=$HOME/android-sdk bash build.sh` → 得到签名 APK
5. 用 `assets/交付说明模板.md` 写交付文档

网页任务跳第 2 步，直接用 `assets/userscript-template.js`。

## 0 环境选择：优先云端

判断"用哪台机器干活"比写代码更靠前：

| 执行环境 | 能做什么 | 建议 |
|---|---|---|
| **云端 Linux（有 Android SDK / apktool）** | 解包、dump 资源、编译、签名，全流程都能跑 | **首选**。`apktool` + `aapt2` + `d8` + `apksigner` 一次装好，反复复用 |
| 本地手机（只有设备） | 不能解包，只能运行时 dump 控件树 | 兜底路线：`assets/NodeDump.java` |
| 本地 PC（有 Windows + adb） | 可解包/可 adb 真机调试 | 可以，与云端等价 |

**你只有手机时**不是不能做，而是少一条腿：定位环节退到运行时 dump（`assets/NodeDump.java`），照样能拿到 id 名，只是不能批量预读。

**工具从哪下、装在哪、怎么验证、装不上的常见坑**：全部写在 `references/setup.md`（Android build-tools / JDK / ecj.jar / apktool / jadx / adb 的官方下载地址 + 约定目录 + 验证命令）。`build.sh` 在缺工具时也会直接打印"期望路径 + 去哪下"，不会只报一行看不懂的错。

## 1 先判断能不能做（走不通就别白干）

| 目标 App 类型 | 能不能做 | 判断依据 |
|---|---|---|
| 原生 / Material 控件 | 能，最稳 | layout 里有 `textInputEditText1`、`rv`、`more` 这类语义化 id |
| Jetpack Compose | 能，但 id 少 | 多数节点没有 resource-id，靠文字定位 |
| WebView / H5 套壳 | 部分能 | 只能读到 WebView 外层和少量 a11y 节点，常要坐标兜底 |
| React Native | 部分能 | 文字节点可读，id 常常是空 |
| Flutter | 差 | 整个页面基本只有一个节点，只能文字或坐标 |
| Unity / 自绘游戏 | 不行 | 全屏一张图，没有控件树，要换图像识别那套 |
| 有验证码 / 付费墙 | 不是点击能解决的 | 自动化绕不过服务端校验 |
| **网页 / H5 站点** | 能，而且最容易 | 源码明文可读，**不存在"反编译难"这一步** |

判断方法看 `references/decompile-and-ids.md` 第 1 节：解包后数一下 layout 文件与 id 命名密度，密度太低就是自绘。

## 2 反编译取控件（这步是真正的门槛）

四步，命令与避坑全在 `references/decompile-and-ids.md`：

1. `apktool d -s` 解包，看 `res/layout/*.xml` 的结构与控件命名
2. `aapt2 dump resources` 导出 **id 名字 ↔ 数值** 全表
3. 对着目标页面挑出「输入框 / 提交按钮 / 列表 / 行内按钮 / 行内标题」这几类节点
4. 记下它们的 **id 名**（不是数值），并在多个页面确认没有重名

**环境里没有 apktool / aapt2 时**：见 `references/decompile-and-ids.md` 第 3 节——要么现装（apktool jar + Android build-tools），要么走"运行时 dump 控件树"的兜底路线，不用反编译也能拿到 id 名。

定位优先级固定：**id > 文字 > 坐标**。三者都拿不到才考虑 OCR。

## 2.5 脚手架：直接复制，别从零写

`assets/` 里有三份可直接用的东西，**先复制再改，不要重新实现**：

| 文件 | 用途 |
|---|---|
| `assets/a11y-apk-template/` | 自制无障碍 APK 完整工程：Manifest、服务配置、`AutoService`（找/点/滑/等/重试/熔断）、`MainActivity`、`build.sh`（无 Gradle，aapt2+d8+zipalign+apksigner）。**已在云端实测能编出签名通过的 APK** |
| `assets/userscript-template.js` | 篡改猴 / 脚本猫脚本模板：脚本头、`waitFor`、完整可见判断、弹窗探测、虚拟列表逐行 |
| `assets/NodeDump.java` | 取控件工具：把节点树打成 `class \| id \| text \| bounds \| clickable`，2 秒节流，`adb logcat -s DumpNode` 看 |
| `assets/check-env.sh` | 环境自检：aapt2/d8/zipalign/apksigner/android.jar/javac 是否齐，缺什么给下载提示 |
| `assets/交付说明模板.md` | 交付文档填空模板：安装、必做、状态栏语义、性能提醒、报错要带什么 |

模板里要改的只有 `AutoService` 顶部那一段 `必改区`（包名 + 6 个 id + 弹窗文字）和 `runTask()` 里的流程步骤。**`build.sh` 在没有 javac 时会自动回退到 ecj，只需 JRE。**

## 3 两种壳，同一份控件清单

拿到清单后分两条路，细节在 `references/shell-recipes.md`：

- **3A 自制无障碍执行器 APK**：完全掌控，能给状态栏、能自动拉起目标 App、能嵌业务逻辑（读 txt、解析数据）。适合"只做一件事的成品"。
- **3B 现成壳**：AutoX.js / AutoJs6 / Hamibot，用户装壳 + 导入脚本。适合"会写一点脚本的人"和多任务共存。

**关键差异**：执行器的思路可以搬，代码不能照抄。自制 APK 用 `AccessibilityNodeInfo` 直接 `performAction`，AutoX.js 用选择器 + 轮询。把 A 的代码贴进 B 会得到一堆跑不通的东西。

## 3C 第三种形态：网页用户脚本（篡改猴 / 脚本猫）

网页侧不走反编译——HTML/CSS/JS 本来就是明文，F12 就能读。所以这里的判断阶梯是：**能调页面自己的接口就直接调，不能才点界面**。App 侧"能发请求就别驱动 UI"是同一个原则。

产出形态是一个 `.user.js` 单文件，用户拖进篡改猴 / 脚本猫即可，**不需要打包、签名、重装**。

细节（定位优先级、等待元素、虚拟列表逐行、脚本头、12 条网页坑、CORS/iframe/限流）见 `references/web-userscripts.md`。

## 4 稳定性：先看这五条

完整 20 条在 `references/pitfalls.md`（现象 → 根因 → 修法），先记住最致命的：

1. **旧节点坐标失效**：滚动/刷新后再用缓存的节点坐标，会越点越偏。每一下点击前重抓。
2. **整页滚动会漏行**：一次翻一屏，边界上的行被跳过。改小步滑（约 1/3 屏高）+ 等惯性停稳。
3. **弹窗慢半拍就重复点同一行**：第二下会把第一下的弹窗顶掉。点之前先探测弹窗是否已在。
4. **输入重复**：填完用旧节点快照回读，看着是空又贴一遍。写入后必须重新抓节点回读。
5. **停因被覆盖**：中途 break 之后，出口无条件写"全部完成"，用户看到的永远是成功。要单独记停因。

## 5 输入契约：先问清这五样

不给齐就开始写，返工概率极高：

1. **目标应用**：APK 文件，或包名 + 应用商店类型（判断能否拿到安装包）
2. **目标页面**：截图（比文字描述准确十倍）
3. **要做什么**：一句人话 + 期望结果（"点 10 次就行 / 直到点不动为止"）
4. **数据来源**：手工输入、本地 txt、还是页面已有列表
5. **运行环境**：云端（能解包）还是只有手机（只能运行时 dump）

## 5.1 输出契约：交付必须包含这五件

1. **控件清单表**：`用途 | id 名 | 类型 | 所在页面`（没有 id 的写明"靠文字：xxx"）
2. **流程步骤**：按"准备 → 输入 → 触发 → 等结果 → 逐行处理 → 收尾"写，每步标明等待条件
3. **交付物**：签名 APK，或 `.user.js`，或脚本文件；**说明改哪几个字段能换应用**
4. **状态栏语义**：每个状态字符串对应哪一环（用户报 bug 时靠它定位）
5. **验证记录**：跑了几项、每项耗时、有没有重复/遗漏
6. **装哪里、怎么开**：交付说明固定写四行——安装包位置/链接、装完要去"设置→无障碍"打开（**每次重装都会被系统清掉，必须重开**）、运行前提（目标应用停在哪个页面）、出问题先看状态栏第一行是否"无障碍：已连接"

## 5.2 验收标准：这三条不过就是没做完

- **连通**：最小集 3 项连续通过，单项耗时 < 10 秒
- **幂等**：同一批跑第二遍结果一致（不重复点、不漏行）
- **可定位**：中途失败时，状态栏能说出"第几项、卡在哪一步"

只满足第一条不算完成——那只是"能跑一次"，不是"能用"。

## 5.5 跑不起来的排查顺序

按这个顺序查，别乱试：

1. **服务连没连上**：界面显示"无障碍：未连接" → 设置里关一次再打开（**每次重装都会被系统清掉**）
2. **设置里勾了但连不上**：`ENABLED_ACCESSIBILITY_SERVICES` 有记录却拿不到实例 → 关掉重开；仍不行就重启手机
3. **点开始没反应**：上一轮线程已死但 `running` 还挂着 true → 心跳超过 15 秒应强制放开
4. **Android 13+ 侧载被拦**：设置里该应用显示"受限设置" → 手动允许后再开无障碍
5. **跑到一半被系统杀掉**：加电池白名单 / 允许后台活动；国产 ROM 还要关"应用自动管理"
6. **点了没效果**：目标节点 `clickable=false` → 往上找可点父节点，或退回坐标
7. **一直等不到结果**：App 没响应 / 请求失败 → 手动操作一次看是否正常，区分"脚本问题"和"应用问题"

## 6 性能与设备：别指望挂一整夜

**这类脚本是"持续消耗型"的，不是"挂上就忘"的。** 16G 运存的旗舰机连续跑一两个小时一样会卡——这不是配置问题，是机制问题。交付前必须向使用者讲明。

### 6.1 为什么会越跑越卡

| 原因 | 机制 |
|---|---|
| 全树遍历 | 每次找控件都是把整个界面树深搜一遍，列表行越多、层级越深，单次扫描越慢（几十到上百毫秒），长任务里累积成明显卡顿 |
| 节点对象堆积 | 抓出来的节点对象不主动释放会一直占内存；脚本里缓存节点还会拿到失效快照 |
| 手势队列积压 | 点击/滑动是排队派发的，前一下没处理完就继续发，会越排越长，表现为"点了没反应，过一会儿连点好几下" |
| 目标 App 自身泄漏 | 反复搜索、反复弹窗，被操作的那个 App 内存会涨，最后它自己先卡 |
| 系统输入法 / 输入框 | 每次聚焦弹键盘、收起，IME 进程也会积累 |
| 屏幕常亮 + 频繁手势 | 发热 → 温控降频 → 更卡，形成正反馈 |

### 6.2 建议的运行策略（写进任何交付物里）

- **单次连续不超过 20–30 项 / 30 分钟**，中间停 1–2 分钟让系统回收
- **低配机（4G 运存以下 / 中低端芯片）单次不超过 10–15 项**，并适当拉长每步等待
- **不要夜间挂机**：无障碍服务与目标 App 都可能被系统回收，回收后不会自己恢复，第二天看到的是"跑了一半就停"
- **不要边充电边长时间跑**：发热叠加热控，卡顿会明显加剧
- **每项记录耗时**：超过阈值（如 30 秒/项）就主动降速或停下，别硬撑
- **跑前把目标 App 从后台清一遍**，减少它自身的内存残留

### 6.3 出现这些现象就该停

- 状态栏/日志里每项耗时逐项变长（1s → 5s → 20s）
- 目标 App 界面开始"转圈变慢"、滑动不跟手
- 点击后要等两三秒才有反应（手势队列已经堆了）
- 手机明显发烫、系统开始杀后台

**这不是"再跑一会儿就好了"，是它在耗尽资源，继续跑只会更糟。**
